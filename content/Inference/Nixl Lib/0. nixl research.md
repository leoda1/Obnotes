## 0. 前言
nixl 就是推理场景下点对点数据传输的 abstract，支持了DRAM，VRAM，文件，块存储，对象存储。==推理的数据路径可能内存->存储，上层框架关心 UCX\GDS\对象存储\其他后端==，nixl直接提供一个统一的northbound 接口，上层只需要描述 buffer 从本地传到远端or本地另一端，backend 由 NIXL 选。
## 1. nixl struct
核心分为以下几大类：
1. `nixlAgent`
NIXL的统一入口，负责创建 backend、注册本地内存、管理远端 metadata、创建传输请求、调度 backend 执行、查询状态和通知。
2. `nixlPluginManager`
负责 backend 插件的发现、加载、缓存和实例化。提供的功能包括：动态/静态插件和用户给个 build。
3. `nixlBackendEngine`
nixl 的向下的接口，flagxc 得有才能runtime 时刻使用 flacx backend。nixlBackendEngine提供了一堆虚函数给我们自己重载 flagcx 对应的实现：
4. `nixlBackendPlugin`
是否 support，然后注册，然后建联，然后 prepare，然后 post，然后 check，然后 release。

## 2. NIXL 注册/传输
NIXL 的一个很核心的设计是：先注册，再传输。
它会把每块注册的内存按 backend 建索引，之后在真正发传输请求时，把用户给的地址范围映射到 backend metadata。用户给的地址到 post 时刻，主要变化就是： `addr / len / devId` -> `地址 + backend metadata` 。
![[0. nixl 调研 2026-03-10 15.32.39.excalidraw.svg]]
%%[[0. nixl 调研 2026-03-10 15.32.39.excalidraw|🖋 Edit in Excalidraw]]%%
1. 用户给 NIXL 的只是 addr / len / devId
2. populate() 会去已注册区间里找“哪个 registration 覆盖了这个地址范围”
3. 找到后，把对应的 metadataP (如果是 remote 还包括了传metaB给远端再==反序列化==为 metaP)填回结果 descriptor
4. 所以后面的 backend 已经不用再做地址查表，它拿到的就是“地址 + backend metadata”

NIXL backend 至少要支持两类 metadata：
* 对应 getConnInfo() / loadRemoteConnInfo()
* 对应 getPublicData() / loadRemoteMD()
## 3. NIXL 的 API 和内部调用链

以上已经介绍了基本的操作，对上的 python 接口这里跳过。这些操作在 nixlAgent内需要自己有一套创建流程。nixl 接口给我们了 `createBackend` 来让我们自己去调用自己的一套具体实现，包括但不局限于：

* 让 PluginManager 找到插件
* 通过插件创建 nixlBackendEngine
* backend 支持 remote，就先拿 getConnInfo()
* backend 支持 local，就先 connect(self)
* backend 支持notification

## 5. 没理解的地方

1. **初始化代码做了什么？**

* `nixlAgentData` 自己的构造函数，分配了一堆 map 和 flag
```
nixlAgentData("AgentA", cfg)
  ├─ 检查环境变量 NIXL_ETCD_ENDPOINTS → 决定 useEtcd = true/false
  ├─ 创建 memorySection = new nixlLocalSection()   ← 一个空的"本地内存登记簿"
  └─ 初始化 telemetry（optional）
```
* `nixlLocalSection`，没构造函数，所以走的基类的 default 构造函数，即拿到 `sectionMap` 和 `memToBackend`这两个空字段。
后续你调 registerMem() 时，登记的内存信息都存在这里。它按 `(内存类型, 后端引擎)` 做索引，比如 VRAM_SEG, UCX引擎 下面挂了哪些 GPU buffer。
* `nixlAgent` 自己的构造函数开了一个监听TCP Listener和后台线程(死循环)

2. **nixl 传递 metadata 的方式包括？**

* 自动模式：**nixlAgent 的成员函数`sendLocalMD/fetchRemoteMD`, 函数内会对四元组`myMD`会标记上有 ip 就走SOCK_SEND，没 ip 就走ETCD_SEND。
```cpp
 // If IP is provided, use socket-based communication
    if (extra_params && !extra_params->ipAddr.empty()) {
        data->enqueueCommWork(std::make_tuple(SOCK_SEND, extra_params->ipAddr, extra_params->port, std::move(myMD)));
        return NIXL_SUCCESS;
    }

#if HAVE_ETCD
    // If no IP is provided, use etcd (now via thread)
    if (data->useEtcd) {
        data->enqueueCommWork(std::make_tuple(ETCD_SEND, default_metadata_label, 0, std::move(myMD)));
        return NIXL_SUCCESS;
    }
    NIXL_ERROR_FUNC << "invalid parameters to be used for either socket or ETCD";
    return NIXL_ERR_INVALID_PARAM;
```
* 手动模式：就直接走 **`getLocalMD` + `loadRemoteMD`的逻辑。

3. **序列化/反序列化和 nixlBackendMD 到底在干嘛？**

### 3a. 为什么 getConnInfo 要序列化 uniqueId+host+dev？

**通俗类比：** getConnInfo 就是**发名片**。

你要跟对方通信，对方得知道怎么找到你。不同后端需要不同的"联系方式"：

|后端|名片里放什么|为什么需要|
|---|---|---|
|UCX|worker address|对方用这个地址创建 endpoint 连过来|
|FlagCX|uniqueId + host_hash + device_id|对方用 uniqueId 做 `flagcxCommInitRank` 建 communicator|

这些信息序列化成一个 blob，通过元数据交换（手动/socket/etcd）传给对端。对端调 loadRemoteConnInfo(blob) 时使用。

### 3b. registerMem 是什么？

**通俗类比：** nixlBackendMD 就是一张**房产证**。

你有一块 GPU 内存（"房子"），registerMem 做了两件事：

1. 告诉后端"我有这块内存"，后端做底层登记（UCX: `ucp_mem_map` 获得 rkey；FlagCX: 分配 token）
2. 返回一个 nixlBackendMD* 指针——这就是这块内存的"房产证"

nixlBackendMD 基类本身确实只有一个 `isPrivateMD` bool 字段。但**每个后端的子类**会加自己的东西：

UCX 的子类:    rkey, ucp_mem_h, ...
FlagCX 的子类: local_mem 句柄, mem_token, base_addr, length, ...

基类只是一个统一句柄，让 NIXL 框架层面可以用统一类型传递，不需要知道后端具体存了什么。

### 3c. 为什么序列化成 token+addr+len？

**通俗类比：** 这是把"房产证"压缩成一个可以邮寄的**摘要**。

getPublicData() 的作用是：把本地注册的内存信息导出成一个**对端可用的摘要**。

对端不需要你完整的底层句柄（它也用不了），它只需要知道：

- **token/rkey**：访问凭证（"钥匙"）
- **addr**：基地址（"门牌号"）
- **len**：范围（"房子多大"）

这样对端在发起传输时就知道：

- UCX: "我要 RDMA write 到远端地址 addr 处，用 `rkey` 做权限校验"
- FlagCX Phase 0: "远端有块 buffer 在 addr，长 `len`"（双边方案只做对齐校验，不用 token 去直接访问）

### 3d. 反序列化后为什么还要返回远端 nixlBackendMD*？

**通俗类比：** 对端收到你邮寄来的"房产证摘要"，要**贴到自己的档案夹里**做本地索引。

loadRemoteMD 做的事：

收到 blob (token=42, addr=0x7f00, len=4096)
  → 解析
  → 创建一个 nixlBackendMD 子类对象（isPrivateMD=false，表示这是远端的）
  → 填入: remote_token=42, base_addr=0x7f00, length=4096
  → 返回这个指针

NIXL 框架把这个指针存到 `remoteSections["AgentB"]` 里。后续你调 `createXferReq(NIXL_WRITE, local_descs, remote_descs, "AgentB")` 时，框架用 `populate()` 从 remoteSection 里查到这个 nixlBackendMD*，挂到 nixlMetaDesc.metadataP 上，传给 prepXfer() / postXfer()。

后端在 postXfer 里拿到这个指针后：

- UCX: 取出 `rkey` → `ucp_put_nbx(remote_addr, rkey, ...)`
- FlagCX: 取出 `remote_token` → 构造 IOV → flagcx_nixl_submit(...)
